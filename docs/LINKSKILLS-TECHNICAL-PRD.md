**Status:** Technical reference for the LiNKskills Program as actually built in this repository (verified against `lib/skill_runtime`, `validator.py`, `scripts/`, `supabase/migrations/`, `skills/`, tests, and CI as of 2026-07-19).

**Ground rule:** Code is the source of truth. Where older docs under `docs/archive/` disagree with code, this document follows the code and calls out the discrepancy in §11.

**Companion:** [`LINKSKILLS-INTENT.md`](./LINKSKILLS-INTENT.md) — why this Program exists.

## 1. System overview / architecture

LiNKskills is a **git-backed skill library**, not a long-lived API service. After ADR 0001, the live surface is:

| Layer | Implementation |
|---|---|
| **Skill packages** | `skills/<skill_id>/` — progressive disclosure (`SKILL.md`, `advanced/`, `examples/`, `references/`, `scripts/`) |
| **Machine catalog index** | `catalog/index.json` — generated by `scripts/build-catalog-index.py` from on-disk skills |
| **Structural gate** | `validator.py` — Golden Template + `format_profile` branching + mandatory `eval-suite.yaml` |
| **Consumer runtime** | `lib/skill_runtime` — catalog load, skill resolve, telemetry writers |
| **Local telemetry buffer** | `execution_ledger.jsonl` |
| **DB schema (when applied)** | Postgres schema `lskills`: `catalog`, `telemetry`, `eval_runs` |
| **Librarian instructions** | `skills/self-improvement/SKILL.md` |
| **Librarian worker** | `LiNKplatform/packages/librarian-runner` (cross-repo) |
| **Tool packages** | `tools/` — global CLI tools; ownership gate via `configs/service_ownership.json` |

### Process topology

```
Authoring path
  skill-architect / skill-template
       → skills/<id>/ artifacts
       → validator.py
       → scripts/build-catalog-index.py → catalog/index.json

Consumer path
  Program host checkout (pinned SHA from main)
       → lib.skill_runtime.load_skill(skill_id)
       → read SKILL.md (+ progressive disclosure as needed)
       → lib.skill_runtime.record_invocation → execution_ledger.jsonl
            └─ optional PostgREST insert → lskills.telemetry

Curation path (async)
  LiNKplatform librarian-runner (scheduled)
       → reads lskills.telemetry + per-skill eval-suite.yaml
       → frontier judge → lskills.eval_runs
       → advances lskills.catalog.certification_state (DB gate + auto-demote)
```

Permission-to-act is **never** decided in this topology. Consumers and the Librarian observe quality; Program Ledgers and `platform.capability_grants` authorize action.

## 2. Terminology glossary

| Term | Meaning |
|---|---|
| **Skill** | A progressive-disclosure package under `skills/<skill_id>/` with `SKILL.md` frontmatter + body |
| **Golden Template** | The authoring shape enforced by `skill-template` + `validator.py` |
| **format_profile** | `simple` \| `heavy` — selects which structural rules the validator enforces (default `heavy`) |
| **Eval suite** | Per-skill YAML at `skills/<id>/references/eval-suite.yaml` — baseline quality scenarios + rubric |
| **certification_state** | Librarian-internal gate: `draft` \| `eval_pending` \| `usable` \| `deprecated`. **Not** tenant activation or entitlement |
| **Catalog index** | `catalog/index.json` — filesystem discovery surface for consumers |
| **lskills.catalog** | DB table: one row per skill **version**, with eval_suite_ref + certification_state |
| **Telemetry** | Observational invocation record (`InvocationEvent` → ledger / `lskills.telemetry`) |
| **execution_ledger.jsonl** | Append-only local buffer at repo root (and optionally on consumer hosts) |
| **Librarian** | Curation process: skill instructions here + runnable agent in LiNKplatform |
| **Consumer Program** | Any LiNKtrend Program that loads skills from a checkout of this repo |
| **Logic Engine** | Retired governance control plane; archived under `archive/logic-engine-2026-07-14/` |

## 3. Skill authoring and validation pipeline

### 3.1 Authoring meta-skills

| Skill | Role |
|---|---|
| `skill-template` | Golden Template scaffold (`format_profile: heavy` body; simple profile documented under `references/simple-profile.md`) |
| `skill-architect` | Modes: `SCAFFOLD`, `REVERSE_ENGINEER`, `REFINER`. Selects `format_profile` (default heavy). Does not execute the target skill's business actions |
| `tool-architect` | Creates/updates global tools under `tools/` |

### 3.2 Progressive-disclosure layout

Every skill directory is expected to contain at least:

- `SKILL.md` — frontmatter + instructions (line-budget enforced by validator)
- `references/` — contracts (`schemas.json`), patterns, changelog, **`eval-suite.yaml` (mandatory)**
- Optional: `advanced/`, `examples/`, `scripts/`

### 3.3 `format_profile` (implemented)

| Aspect | `simple` | `heavy` (default) |
|---|---|---|
| Use when | Stateless single-pass, few tools, no HITL resume | Multi-phase, resumable, HITL, task ledger |
| `persistence.required` | Must not be `true` | Required `true` + `state_path` |
| `.workdir/tasks` / `task_id` / `state.jsonl` protocol | Not required | Required |
| Full Decision Tree / specialist-generalist terms | Not required | Required |
| Eval suite | **Required** | **Required** |
| Ledger / telemetry append | **Required** (Phase 5) | **Required** |
| Folder shape + CLI-first tooling | Required | Required |

**Code:** `validator.py` `VALID_FORMAT_PROFILES`, `resolve_format_profile`, branched checks in `validate_frontmatter` / `validate_body` / `validate_skill_structure`. Default is heavy so absent frontmatter never silently weakens validation.

**On disk today:** most skills omit the field (→ heavy). Explicit `simple` examples include `git-safeguard` and `citation-enforcer`.

### 3.4 `validator.py`

Entrypoint used by CI:

```bash
python3 validator.py --repo-root . --scan-all
```

Enforces (non-exhaustive):

- Frontmatter schema / naming / version discipline
- Folder integrity and contract pointers
- `format_profile` branching (above)
- **`validate_eval_suite`** — every skill must have a non-empty `references/eval-suite.yaml` with `skill_id`, `pass_threshold`, `rubric`, and at least one scenario `id`
- Tool package compliance under `/tools`
- Service ownership via companion script in CI (`scripts/check-service-ownership.py`)

### 3.5 Catalog index build

```bash
python3 scripts/build-catalog-index.py          # write catalog/index.json
python3 scripts/build-catalog-index.py --check  # CI freshness gate
```

`lib/skill_runtime/catalog.py`:

- Discovers `skills/*/SKILL.md`
- Parses flat frontmatter scalars (including nested `min_reasoning_tier`)
- Sets `eval_suite_ref` to `skills/<id>/references/eval-suite.yaml`
- Defaults `certification_state` to `draft` unless a DB overlay map is supplied
- Defaults `format_profile` to `heavy` when absent

## 4. Mandatory eval suite mechanism

### 4.1 On-disk format

Every skill ships `skills/<skill_id>/references/eval-suite.yaml`. Minimal required fields (validator structural checks):

- `skill_id` (must match directory name)
- `pass_threshold`
- `rubric` with ≥1 dimension
- `scenarios` with ≥1 `id`

Designed shape (also what the Librarian loader expects) includes weighted rubric dimensions (optional `hard_fail_below`), success + guardrail scenarios, optional deterministic `assertions`, and `judge.min_reasoning_tier: high|frontier`.

**Coverage today:** all **34** skills under `skills/` have an `eval-suite.yaml` (verified 2026-07-19).

### 4.2 Runner location

This repo validates **presence and structure**. The **executable eval + frontier judge** path lives in `LiNKplatform/packages/librarian-runner`:

- Loads suites via `src/skills/eval-suite-loader.ts`
- Judges via OpenRouter frontier/high tier (`LIBRARIAN_JUDGE_TIER` refuses cheap tiers)
- Writes `lskills.eval_runs` with `rubric_scores`, `overall_score`, `passed`, `delta_vs_previous`, `judge_tier`
- Advances `lskills.catalog.certification_state` only on clean, no-regression improvement

### 4.3 DB gate (when schema applied)

From `supabase/migrations/20260715_000002_lskills_catalog_core.sql`:

- `eval_suite_ref` NOT NULL + non-empty CHECK
- `usable` requires path-shaped `.yaml` ref
- `BEFORE INSERT OR UPDATE` trigger: `usable` only if latest eval_run for `(skill_id, version)` passed
- `AFTER INSERT` on eval_runs: auto-demote currently-`usable` version to `eval_pending` on regression

## 5. Usage telemetry system

### 5.1 `lib/skill_runtime/telemetry.py`

`InvocationEvent` fields:

| Field | Role |
|---|---|
| `skill` | Skill id (legacy ledger key name retained) |
| `status` | `initialized` \| `in_progress` \| `pending_approval` \| `completed` \| `failed` |
| `summary` | Short human-readable summary |
| `task_id`, `skill_version`, `agent_id`, `program_ref` | Attribution |
| `issue_ref`, `run_ref` | Optional Program Ledger linkage (labels, not authz) |
| `duration_ms`, `cost`, `outcome_detail` | Observability |
| `event_id`, `timestamp` | Identity / time |

**Explicitly excluded:** `tenant_id`, entitlements, capability grants, billing tracks — telemetry never gates action.

### 5.2 Write path

`record_invocation(...)`:

1. Always appends JSONL to `execution_ledger.jsonl` (or caller-supplied path).
2. If Supabase URL+key env is present and `write_supabase=True`, POSTs to PostgREST `lskills.telemetry` (`Accept-Profile` / `Content-Profile: lskills`).
3. Supabase failure does **not** undo the local buffer (`supabase: failed` in result dict).

Env resolution (`_supabase_config`):

- `LIBRARIAN_TARGET_ENV=prod` → `LINKTREND_PLATFORM_PROD_SUPABASE_*`
- else stage → `LINKTREND_PLATFORM_STAGE_SUPABASE_*`
- fallbacks: `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`

Flush drain: `python3 scripts/flush-telemetry.py` → `flush_telemetry_buffer`.

### 5.3 Aggregation

`global_evaluator.py` — cross-skill health report from the local ledger (failure/HITL rates, refinement recommendations). Complements, does not replace, Librarian certification.

## 6. Consumer load path

Consumers do **not** call a LiNKskills HTTP API for skill text.

```
1. Sync LiNKskills checkout (full or sparse: skills/ + catalog/) — pin SHA from main
2. Read catalog/index.json → discover skill_id, version, paths
3. Optional: overlay certification_state from lskills.catalog (usable filter)
4. load_skill(skill_id) → SkillBundle (SKILL.md + disclosure paths + eval suite path)
5. After run: record_invocation(...)
```

### 6.1 Python API (authoritative)

```python
from lib.skill_runtime import load_skill, record_invocation, InvocationEvent

bundle = load_skill("git-safeguard", repo_root="/opt/linkskills", require_usable=False)
instructions = bundle.skill_md.read_text()

record_invocation(
    InvocationEvent(
        skill=bundle.skill_id,
        skill_version=bundle.version,
        status="completed",
        summary="Ran pre-push checklist",
        task_id="20260718-1700-GITSAFE-123456",
        agent_id="sites-worker",
        program_ref="lsites",
    ),
    repo_root="/opt/linkskills",
)
```

### 6.2 `require_usable`

- `False` (current default practice): filesystem presence is enough for instruction loading; certification still `draft` in the generated index until Librarian overlays.
- `True`: raises `PermissionError` unless catalog index lists `usable`.

`load_skill` also fails closed if `references/eval-suite.yaml` is missing on disk.

### 6.3 Host bootstrap

See still-live runbook [`runbooks/PRODUCTION_OPERATIONS.md`](./runbooks/PRODUCTION_OPERATIONS.md): clone pinned `main` SHA, Python 3.11+, optional GSM env render, validate, point consumers at checkout via `repo_root` / `LINKSKILLS_REPO_PATH`.

## 7. Librarian curation (cross-repo)

### 7.1 Split of responsibility

| Piece | Location |
|---|---|
| Skill-side workflow / Phases 1–5 instructions | `skills/self-improvement/SKILL.md` (v1.1.0) |
| Agent identity | `LiNKplatform/agents/librarian.md` |
| Runnable orchestration | `LiNKplatform/packages/librarian-runner` |
| DB hard gates | `lskills` triggers/constraints in this repo's migrations |

The Librarian is **one** named agent with standing authority over **two** Programs (LiNKskills certification + LiNKbrain knowledge curation). Its body lives in the neutral cross-Program home so it is not split across product repos.

### 7.2 Skills-half behavior (as implemented in librarian-runner)

1. Review `lskills.telemetry` to prioritize candidates.
2. Load each candidate's `eval-suite.yaml` from `LINKSKILLS_REPO_PATH`.
3. Frontier/high judge → write `lskills.eval_runs` with rubric scores + `delta_vs_previous`.
4. Advance `certification_state` toward `usable` only on clean improvement; else leave `eval_pending` / escalate.
5. Rely on DB auto-demote on regression — do not re-implement that gate in app code.

Invocation model: **async / scheduled** (systemd timer at 02:30 UTC in librarian-runner `ops/`), never mid-session side effect. Prefer `LIBRARIAN_DRY_RUN=true` for first supervised passes.

### 7.3 What this repo still owns for Librarian

- Eval-suite YAML content and validator presence gate
- Schema that enforces usable ↔ passing eval
- Seed migration for catalog rows
- PostgREST exposure migration for telemetry inserts
- Local ledger buffer writers used by consumers and skill Phase-5 appends

## 10. Out of scope / deliberately deferred

Honest gaps — not missing checkboxes on an unfinished catalog shape:

1. **Live Librarian certification of all skills to `usable`** — index defaults to `draft`; `require_usable=False` is correct until real eval_runs exist.
2. **Confirming migration apply on every target env** — SQL is written; ops must verify per environment.
3. **In-repo model-judge eval runner** — structural validation here; full judge execution is in LiNKplatform librarian-runner (by design).
4. **Org-scoped RLS on `lskills.catalog.org_id`** — nullable column is future-proofing only; no authz semantics today.
5. **Dollar-cost dashboard** — `cost` jsonb is observational; no billing ledger.
6. **Long-lived skill-text API** — explicitly rejected; git checkout is the load path.
7. **Root-level historical PRD/SOP/OPERATOR_BRIEFING docs** — still present on disk for history; superseded as source of truth by Intent / Technical PRD / Operations Manual (not moved this pass; see OPEN-ISSUES).
