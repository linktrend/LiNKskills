## 1. System overview / architecture

LiNKskills is LiNKtrend's **procedural-capability platform**: Git remains the editable Skill Pack authority; **published** delivery runs through a LiNKskills Gateway (MCP / HTTP) against LiNKplatform-backed registry and storage (ADR 0002). After ADR 0001, permission-to-act never returns here. ADRs **0002–0008** are accepted alongside ADR 0001.

| Layer | Implementation |
|---|---|
| **Skill packages (editable source)** | `skills/<skill_id>/` — progressive disclosure (`SKILL.md`, `advanced/`, `examples/`, `references/`, `scripts/`) |
| **Machine catalog index (source discovery)** | `catalog/index.json` — generated by `scripts/build-catalog-index.py` |
| **Structural gate** | `validator.py` — Golden Template + `format_profile` + mandatory `eval-suite.yaml` |
| **Domain packages (launch architecture)** | `packages/contracts`, `core`, `publisher`, `eval_runner`, `tool_runtime`, `gateway`, `mcp_server`, `client`, `librarian_domain` |
| **Actor-facing delivery** | stdlib HTTP Gateway + `skills_*` MCP server (in-repo) |
| **Compatibility consumer path** | `lib/skill_runtime` — git-checkout load + ledger writers (**migration window**, not the sole final load path) |
| **Local telemetry buffers** | `execution_ledger.jsonl` + client offline event buffer |
| **DB schema (when applied by Platform)** | Postgres schema `lskills`: catalog / telemetry / eval_runs + additive registry foundation (`20260727_000005`) |
| **Librarian instructions** | `skills/self-improvement/SKILL.md` |
| **Librarian domain worker** | `packages/librarian_domain` (invoked by LiNKplatform generic host) |
| **Librarian host** | `LiNKplatform/packages/librarian-runner` (cross-repo) |
| **Tool packages** | `tools/` — global CLI tools; ownership gate via `configs/service_ownership.json` |
| **Actor integration fragments** | `configs/fragments/` + `docs/integrations/` (Cursor project canary; Codex/OpenClaw handoff) |

### Process topology (internal-launch target)

```
Authoring path
  skill-architect / skill-template
       → skills/<id>/ artifacts
       → validator.py
       → scripts/build-catalog-index.py → catalog/index.json
       → packages/publisher → immutable bundle + hashes

Certification path
  packages/eval_runner (real runner)
       → execute cases with tools / fixtures
       → REJECT prompt-only / fake judges for certification
       → evidence → catalog / profile certification (when DB applied)

Publication path (one-way)
  Git commit → validate → bundle → eval evidence → upload immutable artifacts
       → advance published release in lskills (Platform-backed)
       → Gateway serves published releases only for ordinary execution

Consumer path (steady-state target)
  Actor (Cursor / Codex / OpenClaw / Program executor)
       → skills_* MCP or HTTP /v1/{operation} (packages/gateway + mcp_server)
       → auth via Platform claims (FAKES in-repo until Platform publishes)
       → discover / disclose / run / tool-resolve / feedback
       → packages/client optional SDK + offline buffer

Compatibility / migration path (still present)
  Program host checkout (pinned SHA)
       → lib.skill_runtime.load_skill(skill_id)
       → record_invocation → execution_ledger.jsonl
            └─ optional PostgREST insert → lskills.telemetry
  packages/client compat wrappers ease migration toward Gateway

Curation path (async)
  LiNKplatform librarian-runner (scheduled host)
       → invokes packages/librarian_domain worker contracts
       → reads telemetry + eval evidence
       → proposes certification / improvement (never permission-to-act)
```

Permission-to-act is **never** decided in this topology. Consumers and the Librarian observe quality; Program Ledgers and `platform.capability_grants` authorize action.

**Brain separation:** LiNKbrain exposes `brain_*` through its own service. There is no combined Brain/Skills Gateway and no shared mutable domain table.

## 3. Skill authoring and validation pipeline

### 3.1 Authoring meta-skills

| Skill | Role |
|---|---|
| `skill-template` | Golden Template scaffold (`format_profile: heavy` body; simple profile documented under `references/simple-profile.md`) |
| `skill-architect` | Modes: `SCAFFOLD`, `REVERSE_ENGINEER`, `REFINER`. Selects `format_profile` (default heavy). Does not execute the target skill's business actions |
| `tool-architect` | Creates/updates global tools under `tools/` |

### 3.2 Progressive-disclosure layout

Every skill directory is expected to contain at least:

- `SKILL.md` — frontmatter + instructions (line-budget enforced by validator)
- `references/` — contracts (`schemas.json`), patterns, changelog, **`eval-suite.yaml` (mandatory)**
- Optional: `advanced/`, `examples/`, `scripts/`

Launch Skill Pack fields and disclosure fragments are defined in ADR 0004 and produced into immutable bundles by `packages/publisher`.

### 3.3 `format_profile` (implemented)

| Aspect | `simple` | `heavy` (default) |
|---|---|---|
| Use when | Stateless single-pass, few tools, no HITL resume | Multi-phase, resumable, HITL, task ledger |
| `persistence.required` | Must not be `true` | Required `true` + `state_path` |
| `.workdir/tasks` / `task_id` / `state.jsonl` protocol | Not required | Required |
| Full Decision Tree / specialist-generalist terms | Not required | Required |
| Eval suite | **Required** | **Required** |
| Ledger / telemetry append | **Required** (Phase 5) | **Required** |
| Folder shape + CLI-first tooling | Required | Required |

**Code:** `validator.py` `VALID_FORMAT_PROFILES`, `resolve_format_profile`, branched checks in `validate_frontmatter` / `validate_body` / `validate_skill_structure`. Default is heavy so absent frontmatter never silently weakens validation.

**On disk today:** most skills omit the field (→ heavy). Explicit `simple` examples include `git-safeguard` and `citation-enforcer`.

### 3.4 `validator.py`

Entrypoint used by CI:

```bash
python3 validator.py --repo-root . --scan-all
```

Enforces (non-exhaustive):

- Frontmatter schema / naming / version discipline
- Folder integrity and contract pointers
- `format_profile` branching (above)
- **`validate_eval_suite`** — every skill must have a non-empty `references/eval-suite.yaml` with `skill_id`, `pass_threshold`, `rubric`, and at least one scenario `id`
- Tool package compliance under `/tools`
- Service ownership via companion script in CI (`scripts/check-service-ownership.py`)

### 3.5 Catalog index build

```bash
python3 scripts/build-catalog-index.py          # write catalog/index.json
python3 scripts/build-catalog-index.py --check  # CI freshness gate
```

`lib/skill_runtime/catalog.py` (compatibility path):

- Discovers `skills/*/SKILL.md`
- Parses flat frontmatter scalars (including nested `min_reasoning_tier`)
- Sets `eval_suite_ref` to `skills/<id>/references/eval-suite.yaml`
- Defaults `certification_state` to `draft` unless a DB overlay map is supplied
- Defaults `format_profile` to `heavy` when absent

Steady-state published discovery is Gateway `skills_list` / `skills_search` against published releases — not a required local checkout.

## 4. Mandatory eval suite mechanism

### 4.1 On-disk format

Every skill ships `skills/<skill_id>/references/eval-suite.yaml`. Minimal required fields (validator structural checks):

- `skill_id` (must match directory name)
- `pass_threshold`
- `rubric` with ≥1 dimension
- `scenarios` with ≥1 `id`

Designed shape includes weighted rubric dimensions (optional `hard_fail_below`), success + guardrail scenarios, optional deterministic `assertions`, and `judge.min_reasoning_tier: high|frontier`.

**Coverage:** all **34** skills under `skills/` have an `eval-suite.yaml`.

### 4.2 Real Eval Runner (in-repo)

`packages/eval_runner` is the **real** execution path for certification evidence:

- Loads suites, prepares workspaces/fixtures, executes cases when outputs/tools allow
- Marks non-executable prompt-only cases explicitly (`not_executable_prompt_only`)
- **Certification hard-rejects** FakeJudge / PromptOnlyJudge and any suite containing prompt-only cases (`linkskills_eval_runner.certify`, `linkskills_core.certification`)
- Emits evidence suitable for profile certification (ADR 0006)

Structural presence validation remains in `validator.py`. Cross-repo Librarian frontier-judge orchestration in `LiNKplatform/packages/librarian-runner` continues to participate in scheduled curation; it does **not** authorize prompt-only certification as a substitute for the real runner gate.

### 4.3 DB gate (when schema applied)

From `supabase/migrations/20260715_000002_lskills_catalog_core.sql`:

- `eval_suite_ref` NOT NULL + non-empty CHECK
- `usable` requires path-shaped `.yaml` ref
- `BEFORE INSERT OR UPDATE` trigger: `usable` only if latest eval_run for `(skill_id, version)` passed
- `AFTER INSERT` on eval_runs: auto-demote currently-`usable` version to `eval_pending` on regression

Additive registry surfaces for runs/releases/channels ship in `20260727_000005` (see §8).

## 5. Usage telemetry system

### 5.1 Compatibility writers — `lib/skill_runtime/telemetry.py`

`InvocationEvent` fields:

| Field | Role |
|---|---|
| `skill` | Skill id (legacy ledger key name retained) |
| `status` | `initialized` \| `in_progress` \| `pending_approval` \| `completed` \| `failed` |
| `summary` | Short human-readable summary |
| `task_id`, `skill_version`, `agent_id`, `program_ref` | Attribution |
| `issue_ref`, `run_ref` | Optional Program Ledger linkage (labels, not authz) |
| `duration_ms`, `cost`, `outcome_detail` | Observability |
| `event_id`, `timestamp` | Identity / time |

**Explicitly excluded:** `tenant_id`, entitlements, capability grants, billing tracks — telemetry never gates action.

### 5.2 Compatibility write path

`record_invocation(...)`:

1. Always appends JSONL to `execution_ledger.jsonl` (or caller-supplied path).
2. If Supabase URL+key env is present and `write_supabase=True`, POSTs to PostgREST `lskills.telemetry` (`Accept-Profile` / `Content-Profile: lskills`).
3. Supabase failure does **not** undo the local buffer (`supabase: failed` in result dict).

Env resolution (`_supabase_config`):

- `LIBRARIAN_TARGET_ENV=prod` → `LINKTREND_PLATFORM_PROD_SUPABASE_*`
- else stage → `LINKTREND_PLATFORM_STAGE_SUPABASE_*`
- fallbacks: `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`

Flush drain: `python3 scripts/flush-telemetry.py` → `flush_telemetry_buffer`.

### 5.3 Gateway-observed telemetry (launch path)

The Gateway records structured run lifecycle / feedback operations it directly observes (`skills_run_*`, `skills_feedback_submit`, etc.). `packages/client` provides an offline event buffer for deferred flush. Cooperative ledger append remains available during migration; steady-state delivery must not depend solely on consumers remembering to call `record_invocation`.

### 5.4 Aggregation

`global_evaluator.py` — cross-skill health report from the local ledger (failure/HITL rates, refinement recommendations). Complements, does not replace, Eval Runner certification or Librarian curation.

## 6. Consumer load paths

### 6.0 Authority: steady-state vs migration window

| Path | Role |
|---|---|
| **Gateway MCP/HTTP + published releases** | Steady-state internal-launch consumer delivery (ADR 0002 / 0003) |
| **`lib/skill_runtime` git checkout** | **Compatibility / migration window** — still supported and tested; **not** the final sole load path |

Consumers should plan migration toward Gateway adapters. New work must not treat checkout-only loading as the end-state architecture.

### 6.1 Steady-state target (Gateway)

```
1. Actor authenticates with Platform claims (fakes in-repo until Platform publishes)
2. skills_list / skills_search → discover published skills
3. skills_describe / skills_fragment_get → progressive disclosure
4. skills_run_start → … → skills_run_complete / skills_run_fail
5. skills_tool_resolve / skills_tool_invoke as required by the certified profile
6. skills_feedback_submit / offline client buffer as needed
```

Primary MCP namespace: **`skills_*` only**. HTTP surface: stdlib server in `packages/gateway` (`GET /health`, `GET /ready`, `POST /v1/{operation}`). `/health` and `/ready` describe **process liveness of a local server instance**, not studio-wide stage/prod readiness.

### 6.2 Compatibility path — Python git checkout

```
1. Sync LiNKskills checkout (full or sparse: skills/ + catalog/) — pin SHA from main
2. Read catalog/index.json → discover skill_id, version, paths
3. Optional: overlay certification_state from lskills.catalog (usable filter)
4. load_skill(skill_id) → SkillBundle (SKILL.md + disclosure paths + eval suite path)
5. After run: record_invocation(...)
```

```python
from lib.skill_runtime import load_skill, record_invocation, InvocationEvent

bundle = load_skill("git-safeguard", repo_root="/opt/linkskills", require_usable=False)
instructions = bundle.skill_md.read_text()

record_invocation(
    InvocationEvent(
        skill=bundle.skill_id,
        skill_version=bundle.version,
        status="completed",
        summary="Ran pre-push checklist",
        task_id="20260718-1700-GITSAFE-123456",
        agent_id="sites-worker",
        program_ref="lsites",
    ),
    repo_root="/opt/linkskills",
)
```

`packages/client/linkskills_client/compat.py` wraps Gateway operations so existing Python consumers can migrate without an immediate cutover.

### 6.3 `require_usable` (compatibility loader)

- `False` (current default practice): filesystem presence is enough for instruction loading; certification still `draft` in the generated index until overlays / published certification exist.
- `True`: raises `PermissionError` unless catalog index lists `usable`.

`load_skill` also fails closed if `references/eval-suite.yaml` is missing on disk.

### 6.4 Host bootstrap / actor fragments

- Checkout bootstrap runbook: [`runbooks/PRODUCTION_OPERATIONS.md`](./runbooks/PRODUCTION_OPERATIONS.md) (still relevant for source hosts and migration).
- Cursor product canary: **project-scoped only** — `configs/fragments/cursor-skills-canary.mcp.json.example` + `docs/integrations/cursor/CANARY.md`.
- Codex / OpenClaw: configuration **fragments handed off** (`configs/fragments/*`, `docs/integrations/{codex,openclaw}/HANDOFF.md`) — **not applied** from this repository to shared host config or OpenClaw internals.

## 7. Librarian curation (cross-repo)

### 7.1 Split of responsibility

| Piece | Location |
|---|---|
| Skill-side workflow / Phases 1–5 instructions | `skills/self-improvement/SKILL.md` |
| LiNKskills-specific domain worker / contracts | `packages/librarian_domain` (ADR 0008) |
| Agent identity | `LiNKplatform/agents/librarian.md` |
| Generic runnable host / scheduler | `LiNKplatform/packages/librarian-runner` |
| DB hard gates | `lskills` triggers/constraints in this repo's migrations (Platform applies live) |

The Librarian is **one** named institutional agent with standing authority over **two** Programs (LiNKskills certification + LiNKbrain knowledge curation). Its body lives in the neutral cross-Program home so it is not split across product repos. Domain rules stay in each Program.

### 7.2 Skills-half behavior

1. Review telemetry / candidates (Gateway-observed + ledger / DB when available).
2. Load each candidate's eval suite / published evidence requirements.
3. Require real eval evidence; refuse prompt-only certification shortcuts.
4. Advance certification toward `usable` / certified profiles only on clean improvement; else leave pending / escalate.
5. Rely on DB auto-demote on regression — do not re-implement that gate in app code.
6. Never grant Program permission-to-act.

Invocation model: **async / scheduled** via Platform host, never mid-session side effect. Prefer dry-run for first supervised passes.

### 7.3 What this repo still owns for Librarian

- Eval-suite YAML content and validator presence gate
- Real Eval Runner + certification refusal of prompt-only evidence
- Schema that enforces usable ↔ passing eval (+ additive registry package)
- Seed / PostgREST / registry migrations (authored here; Platform applies)
- Domain worker package and conformance fixtures
- Local ledger / client buffers used during migration

## 10. Gateway / MCP operations (summary)

Independently named `skills_*` operations (HTTP `/v1/{operation}` and MCP tools share the domain service), including:

- Catalog / disclosure: `skills_list`, `skills_search`, `skills_describe`, `skills_fragment_get`, `skills_release_get`
- Run lifecycle: `skills_run_start`, `skills_run_update`, `skills_run_complete`, `skills_run_fail`
- Tools / validation: `skills_tool_resolve`, `skills_tool_invoke`, `skills_input_validate`, `skills_output_validate`
- Feedback: `skills_feedback_submit`, `skills_trace_candidate_submit`

Auth today: production paths use `PlatformClaimsVerifier` with an injected Platform-approved cryptographic authenticator (`LINKSKILLS_PLATFORM_AUTHENTICATOR`). Unsigned `platform.<base64url(JSON)>` is accepted only by `LocalUnsignedClaimsVerifier` under explicit `LINKSKILLS_AUTH_MODE=local-test` (or an injected local-test verifier). Gateway/MCP startup fails closed when production authenticator/config is missing. Competing `fake.*` tokens are rejected. Live Platform issuer and signing keys remain a Platform gate. Spoofed identity keys in request bodies are rejected.

## 13. How to verify (structural — not live readiness)

```bash
python3 validator.py --repo-root . --scan-all
python3 scripts/build-catalog-index.py --check
python3 -m unittest discover -s tests/skill_runtime -v
# Package tests (as present under tests/):
python3 -m unittest discover -s tests -v
python3 scripts/check-service-ownership.py
```

CI (`.github/workflows/ci.yml`) runs catalog gates on PRs and pushes to `development` / `staging` / `main`. Branch source policy enforces promotion lineage (`.github/workflows/branch-source-policy.yml`).

Passing unit tests and a local Gateway `/health` response **do not** constitute stage/prod launch readiness.
