## Practical method

1. **Frame decision and causal hypothesis.** State what decision the research should inform, its horizon, and what evidence could disconfirm the proposed explanation. Keep observed association separate from causal interpretation.
2. **Freeze temporal semantics first.** For each observation capture event timestamp, publication/availability timestamp, source vintage, and timezone/session convention. Use only facts available at the simulated decision instant. For company fundamentals, retain source and release time/vintage alongside fiscal period; fiscal period alone cannot establish point-in-time availability.
3. **Define the observation grain.** State whether the method needs trades, quotes, bars, level-1/2/3 book, instrument definitions, or custom events. Declare bar source and aggregation boundaries (trade, quote, or bar-to-bar), session alignment, and whether an information-driven bar requires trade aggressor data. Check that the simulated venue book type can consume the supplied data; do not infer L2/L3 from bars or top-of-book. Do not treat a bar close as an order-book fill or collapse own-order state into public depth. For book-based claims, preserve book sequence/integrity and whether own orders are included or removed.
4. **Specify model types and units.** Provide canonical instrument identity, currency, quantity/price precision, tick/lot/multiplier, and conversions. Validate price and size at the boundary. A floating display value is not a safe substitute for exact venue precision; Eric must inspect current LiNKtrading types and dependency contracts.
5. **Write the signal definition before translating it.** For Pine, preserve original formula, bar-close/repainting and higher-timeframe/context rules, session/timezone, warm-up, `na`/missing propagation, and visual versus actionable outputs. Separate inputs, state, signal, sizing/risk, alerts, and chart rendering. Build supplied-vector parity cases for historical and boundary bars. Do not mechanically shift every series one bar or add epsilon to divisions; either can change semantics. Optimize/vectorize only after parity is demonstrated.
6. **Make strategy lifecycle explicit.** Describe inputs/events, state transitions, entry/exit/modify/cancel intent, order identifiers, partial/late/rejected states, and which step merely proposes versus effects an approved action. Keep pure analysis and advisory risk calculations away from side-effect boundaries. No order is sent from this reference workflow.
7. **Choose a simulation model that matches the question.** Name venue/book granularity, matching/fill assumptions, latency, queue priority, partial fills, fee schedule source, spread/slippage, funding/borrow and rejected orders. If only bars exist, state that queue/fill realism is unresolved; record the bar timestamp convention and assumed OHLC path, especially when stop and target can both be touched in one bar. Do not present an adaptive high/low order heuristic as observed market path or evidence unless independently supported for this dataset. Record whether displayed liquidity can be reused across fills and whether queue priority is empirical or heuristic. A best-price/unlimited-liquidity model is an optimistic logic check, not an execution estimate. Run sensitivity scenarios instead of presenting optimistic matching as actual execution evidence. The pinned backtest source itself warns that simplistic aggressor assumptions can overstate market-making fills; treat this as a reason to test sensitivity, not as a transferable numerical correction factor.
8. **Control research leakage and selection.** Check lookahead, survivorship/universe history, corporate actions/splits, publication vs fiscal dates, duplicate issuers/joint filers, currency conversion, missing values, and use of revised data. Separate training, validation, and held-out evaluation by date; document all tried variants and selection criteria to expose multiple-testing/overfitting risk.
9. **Bind the experiment to existing records.** Record code revision, parameters/config, dataset/vintage, universe, features, seed, date split, evaluation code/version, and produced output identifiers in the existing LiNKtrading task/Program Ledger. Do not introduce a registry schema, runtime JSON/JSONL file, or parallel experiment database from the source example.
10. **Separate backtest from live and request owner verification.** Eric checks exact engine/dependency APIs, adapter capabilities, lifecycle/reconciliation, tests and supported behavior against current sources. The pinned live guide describes recovery that can infer fills and synthesize orders to force position alignment; it also suggests destructive cache/account actions for persistent discrepancies. Do not import these as Jane or LiNKtrading behavior. A mismatch or uncertain submit remains a hold for the existing owner-controlled reconciliation path; no synthetic corrective order, cache deletion, account flattening, or automatic retry may be recommended from this note. A successful historical simulation is not an order authorization or proof of live execution. State the concrete evidence needed before any downstream approval, then leave the transition to the established owners and two-channel gate.

## Technical distinctions to preserve

- **Data/catalog:** data ingestion, parsing, serialization, catalog and cache have their own provenance and timestamp rules. The source distinguishes exchange/event time from object-initialization time and warns their clocks may not be synchronized; do not treat `ts_init` as authoritative receive time without checking the actual owner contract. Bar aggregation source and interval boundaries also affect signal and execution timing. Do not assert current class names, file formats, schema compatibility, or migration behavior from the pinned sources. The research contract names the facts and behavior; Eric maps them into current LiNKtrading.
- **Domain model:** instrument IDs, currency, price precision, quantity precision, enums and contract metadata are a semantic boundary. Identify units and constraints before strategy calculations or adapter mapping.
- **Order book:** L1 top-of-book, L2 aggregated levels and L3 order-level state answer different questions. Public depth and own-order-inclusive depth can differ. Record the source's book semantics and integrity; do not infer queue position from bar history.
- **Signals and aggregation:** indicator inputs, bar aggregation, custom events, warm-up and timing must be consistent from research to replay/simulation. A signal output needs its observation time and eligibility time; no future/unfinished bar can leak into the decision.
- **Backtest engine and fills:** an engine's event order, simulated venue, book type, matching/fill model, fees and latency are assumptions. Historical books may be immutable and repeatedly reusable unless consumption tracking is enabled; a queue estimate is not exact queue priority. Bar execution imposes a timestamp convention and synthetic OHLC sequence, which can decide whether a stop or target fills first. A result should identify each assumption, include relevant sensitivity and avoid implying that a backtest forecast equals realized performance.
- **Strategy and lifecycle:** strategy logic, actor/indicator state, risk calculation and execution adapters are separate ownership/lifecycle concerns. Jane specifies expected behavior; Eric chooses the applicable LiNKtrading component and implementation.
- **Adapters:** data client, instrument provider, and execution client have distinct responsibilities, transports and failure states. Requirements should identify each capability and its owner rather than assume one adapter does all three.
- **Pine translation:** fidelity comes before optimization. Preserve data context, time and null semantics, then compare outputs over exact input fixtures. The upstream examples contain version-specific syntax and blanket shifts/epsilon patterns; do not copy them.
- **Quant review:** check point-in-time availability, survivorship, split/corporate-action handling, currencies, duplicates, NaN propagation, realistic transaction costs, and reproducibility. Treat these as review questions to answer from supplied evidence, not an automatic grade.
- **Experiment identity:** reproducibility needs the complete data/config/code/universe/features/seed/split/evaluation identity, not just a model file hash. Route into the existing Program Ledger; the source's standalone registry/storage implementation is excluded.
- **Live lifecycle and reconciliation:** boot/shutdown, component lifecycle, order/fill/position readback and recovery need exact current owner rules. The pinned guide explicitly describes inferred fills and synthesized reconciliation orders for position differences, plus advice to clear cached state or flatten an account. Those are upstream behaviors/recommendations, not approved LiNKtrading repair rules. If actual and expected states disagree, hold and escalate; do not auto-create or cancel orders, discard state, or flatten to “repair” a discrepancy.

- All Nautilus-specific class names, config fields, method signatures and runtime behavior are pinned-source hints only. This source has no root license, so none of its text/code is copied; its use here is limited to independently expressed research questions. Any future implementation must be based on current LiNKtrading code and Eric's direct dependency/source review, not copied snippets.

- Do not carry backtest example defaults, fills, fees, latency, or numeric performance claims into a recommendation without evidence for the actual venue/data. Record values and units with source and timestamp; absent values remain assumptions.
- Pine conversion rules must be semantic and testable. A global one-bar shift can remove valid same-bar behavior or fail to prevent lookahead; an epsilon can alter numeric results. Use exact reference inputs and per-series parity requirements.
- The pinned live-concepts support details reconciliation that may generate inferred fill events and synthetic orders, resolve missing in-flight orders to terminal states, and recommends dropping cache or flattening an account in persistent mismatch cases. None is adopted here as an approved recovery rule. A reconciliation mismatch/timeout is an uncertainty hold for the existing owner path, not a Jane action; no state deletion, account flattening, synthetic order, or resend recommendation.
- A signal or backtest result has no live authority. Jane can recommend and explain; Eric implements only through the current approved system, and independent Lisa+Carlos exact-version/two-channel approval remains required for downstream effects.
